# Security policy

## Report a problem privately

Do not open a public issue, a public discussion, or a pull request for a
security problem.

Use the GitHub **Security** tab of this repository and select **Report a
vulnerability**. That opens a private advisory that only the repository owner
can read. If private reporting is not available to you, contact the repository
owner directly through the contact details on their GitHub profile.

Include:

- What the problem lets an attacker do.
- The steps to reproduce it, or a short proof.
- The version, commit, or image tag you tested.
- Your deployment shape, for example the reverse proxy in front of the app.

The owner acknowledges a report and states whether it is accepted or refused.
NotesApp is a one-person project, so there is no service level agreement.
Please give the owner reasonable time to release a fix before you publish.

## Supported versions

Only the newest release and the `main` branch get fixes. There is no long-term
support branch.

## Trust model

Read this before you decide what is a vulnerability.

- **The server operator can read every note.** Notes are stored so that the
  server can index and search them. There is no end-to-end encryption. The
  operator, and anyone with database or disk access, can read the content. In
  a personal installation the operator and the user are the same person.
- **There is one user.** The setup screen creates that account and then closes.
  There is no second account, no sharing, no invitation, and no public page.
- **Disk encryption is the operator's job.** The product expects encrypted host
  storage for the database, the attachments, temporary files, swap, crash
  output and backups. See
  [docs/guide/self-hosting.md](docs/guide/self-hosting.md).
- **HTTPS is the operator's job.** The application publishes a plain HTTP
  listener on the loopback address. Put a reverse proxy that terminates HTTPS
  in front of it.
- **The origin is required.** `NOTESAPP_ORIGIN` has no default. Cookies and
  absolute URLs belong to that origin, and a request that names another host is
  refused.

## In scope

- Reading, changing or deleting notes, attachments or history without a valid
  session.
- Escaping the single-user boundary, for example creating a second account
  after setup.
- Cross-site scripting through note content, an attachment, a diagram or a
  rendered link.
- Cross-site request forgery, session fixation, or a cookie that leaves its
  origin.
- Escaping the row level security of the database with the runtime role.
- Reading note text, search text, credentials or tokens from a log, an error
  message or a metrics answer.
- A path traversal or an unchecked file type in the attachment store.
- A dependency with a known exploitable vulnerability that this product
  reaches.
- A default in `docker-compose.yml` or `.env.example` that exposes an
  installation.

## Out of scope

- The operator reading the notes of their own installation.
- An attack that needs the operator's host account, database credentials, or
  physical access.
- A missing HTTPS header on an installation that has no reverse proxy in front
  of it.
- Denial of service by the single user against their own installation, for
  example a very large note.
- A report generated by a scanner with no proof that the product reaches the
  code.
- Social engineering of the repository owner.
