# Engineering health audit: tests, tooling, build, CI, dependencies, docs, hygiene

Audited on 2026-09-10 against commit `40eebba`.

Repository: `/home/bkhanale/workspace/bkhanale/notesapp`
Branch `main` at `40eebba`, working tree clean, one commit ahead of `origin/main`.
Date of audit: 2026-09-10. Read-only. No build or test suite was run.

## Summary

The engineering base is strong for a one-person project. There are 423 unit test
cases in 39 files, 193 integration test cases in 14 files against real
PostgreSQL, and 24 active browser journeys. The browser tests use accessible
roles, web-first assertions, and no fixed delays. `pnpm verify` is one command
and it is complete for source, contract, types, lint, format, unit, integration,
and builds.

The three biggest problems are:

1. CI never runs the browser tests. `.github/workflows/ci.yml` runs `pnpm
verify` and the two performance gates only, so every P0 user journey is
   verified only when a person remembers to run `pnpm test:e2e`. This breaks the
   rule in `AGENTS.md`.
2. The documentation set does not describe the current product. Two design
   documents, two plan documents, and parts of five development documents still
   describe conflict branches, invitations, members, and SSO. `docs` is 4,011
   lines and about half of it is plan history, not a guide.
3. Repository hygiene blocks a public v0.1. `docker-compose.yml` ships a private
   IP address as its default origin, `rules/03-requestly.md` and the generated
   `AGENTS.md` publish an employer's Jira process, and there is no
   `CONTRIBUTING.md`, `CHANGELOG.md`, or `SECURITY.md`.

## Test strategy assessment

**Robustness: good.** There are no fixed waits in any spec. The only two timers
in the whole suite are a 50 ms readiness poll in `tests/e2e/support/stack.ts:57`
and a 10 ms wait in `tests/integration/sync.test.ts:325`. Save state is read
through `expect.poll` on a `data-save-state` attribute
(`tests/e2e/support/account.ts:44-58`), which is a durable fact and not a
label. Every locator uses an accessible role, label, or id. The `checkedPage`
fixture at `tests/e2e/support/stack.ts:126-147` fails a test on any unexpected
console or page error, which is a strong extra assertion. There are no `skip`,
`fixme`, or `todo` markers in unit or integration tests. All five `test.skip`
calls in the browser suite are project selectors with a stated reason, not
disabled tests.

**Weak points.** Four items: the conditional drawer branch (ENG-17), the WebKit
offline reconnect (ENG-18), the backlinks assertion that only checks the empty
state (`tests/e2e/features.spec.ts:52`), and a wall-clock assertion
`expect(Date.now() - startedAt).toBeLessThan(10_000)` at
`tests/e2e/notes.spec.ts:40`, which is a performance check inside a functional
test and will be the first thing to fail on a slow CI runner.

**Matrix proportionality: too wide for its value.** 8 tests across 5 projects
gives 40 invocations, 16 of which are skipped, so 24 run. Each project starts
its own worker-scoped stack: one disposable PostgreSQL database, 11 migrations,
a real Fastify server, and a free-port reservation
(`tests/e2e/support/stack.ts:63-112`). The first-user test starts a sixth stack
inside the test (`tests/e2e/first-user.spec.ts:20`). With `workers: 1` and
`fullyParallel: false` this is fully serial, and it runs after a complete
`pnpm build`. Chromium runs all 8, Firefox and WebKit 5 each, phone and tablet 4
each. The phone and tablet projects are Desktop Chrome with a viewport override,
which `docs/development/verification.md:33-36` correctly admits is not device
evidence. Cutting the tablet project and enabling `workers: 2` or CI sharding
would cut the wall time by roughly half with almost no loss of signal.

**Integration setup: simple and well designed.** `compose.test.yaml` binds
`127.0.0.1:55432` so it cannot collide with a host PostgreSQL, pins the image by
digest, and initialises a non-superuser migration role in
`tools/test-database/init.sql` so row-level security is proved under the real
role model. `tests/integration/support/database.ts:85-108` creates one
throwaway database per test file, refuses to run unless the server URL names a
`notesapp_test` database (`:63-72`), and drops only what it created.
`tools/test-database/ensure-postgres.sh` uses an isolated Compose project name
and matches by exact label, so it cannot touch a production stack. This is the
strongest part of the tooling. The one gap is ENG-32: neither
`pnpm test:integration` nor `pnpm test:e2e` starts the service, so a first-time
contributor gets a connection error instead of a running database.

## Verification pipeline assessment

`pnpm verify` (`package.json:30`) runs, in order: contract lint, generated-file
comparison, type check of 5 project graphs, version policy plus type-aware
oxlint plus boundary check, Prettier, unit tests, integration tests, and all
builds. That is complete for everything except the browser and the two
performance gates.

Speed problems, in order of cost:

1. `test:integration` triggers a full `pnpm build` including the Vite web build,
   and `verify` then builds again (ENG-15).
2. `typecheck` compiles the root tools project, every workspace project, and
   three extra project graphs (`tests/integration`, `tests/e2e`,
   `tools/performance`), and `build` repeats most of that work.
3. `skipLibCheck: false` in `tsconfig.base.json:16` is correct policy but slow,
   and four projects already opt out of it.

Missing from the pipeline: browser tests in CI (ENG-01), coverage (ENG-22),
dependency audit (ENG-21), a total-transfer or precache budget (ENG-12), a
licence notice step (ENG-24), and any published artefact that records what the
last run measured (ENG-05, ENG-33).
